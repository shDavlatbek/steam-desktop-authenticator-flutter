# Steam Guard Telegram bot

A Telegram front-end for the Steam Desktop Authenticator in this repo. You get
the app's functionality in chat; people you choose get exactly one capability —
approving a QR sign-in for an account you shared with them.

Built with [aiogram](https://docs.aiogram.dev) 3.30 on Python 3.10+.

## Read this before you share anything

**Approving a QR login signs that person into the Steam account.** It is a real,
fully logged-in web session, not a peek. They can browse the account, see the
inventory, and start trades.

What it does *not* give them:

- **The authenticator itself.** The `shared_secret` never leaves this host. They
  cannot generate Steam Guard codes.
- **The ability to finish a trade or market listing.** Those need a mobile
  confirmation, which only you can approve through this bot. That is the real
  boundary, and it is a meaningful one.
- **Anything else in the bot.** Guests cannot list accounts, read codes, view
  confirmations, import, or export. Handlers re-check the share registry on
  every callback, so revoking access takes effect immediately — even mid-flow.

You are notified every time a guest approves or denies a login. That message is
your audit trail.

Two further realities worth being clear-eyed about: this bot's data directory
holds every `shared_secret` you import, so treat the host as sensitive and set
`SDA_PASSKEY`. And Telegram bot chats are not end-to-end encrypted — Telegram's
servers see the QR images and messages that pass through.

## Setup

```bash
cd telegram-bot
python -m venv .venv
.venv/Scripts/activate        # Windows;  source .venv/bin/activate elsewhere
pip install -r requirements-dev.txt   # requirements.txt alone omits pytest

cp .env.example .env          # then fill in BOT_TOKEN and ADMIN_ID
python -m bot
```

To run it in production instead, see [Deploying](#deploying).

`BOT_TOKEN` comes from [@BotFather](https://t.me/BotFather). `ADMIN_ID` is your
numeric Telegram ID — [@userinfobot](https://t.me/userinfobot) will tell you, or
start the bot and send `/whoami`.

Set `SDA_PASSKEY` to encrypt the stored `.maFile`s at rest. Without it they sit
in `DATA_DIR` as plaintext JSON containing your secrets.

## Getting accounts in

Two routes, and they do different things:

- **`/import`** — bulk import. Carries the `shared_secret` and
  `identity_secret`, so it is the only route that enables Steam Guard codes,
  confirmations, and login approval. See below.
- **`/login`** — scan a QR code with the Steam mobile app. No password is typed
  into Telegram, so none is left in the chat history. Stores the session; on an
  account you already have, it just refreshes the login.

`/login` does not move the authenticator — codes and confirmations stay
unavailable until you `/import` the maFile too.

### Bulk import

`/import` stays open until you send `/done`, so you can pile things in:

- **Any number of `.maFile` documents**, one after another or selected together
  as an album.
- **A `.zip` of an entire `maFiles` folder.** Nested folders are fine, and
  non-maFile entries are ignored.

Each upload reports what landed and what was skipped, with a reason per file.
One bad file never stops the rest.

**Encrypted accounts.** A zip that includes its `manifest.json` can be
decrypted here, because the per-entry salt and IV live in that manifest — run
`/import your-passkey` first, then send the zip. A *lone* encrypted `.maFile`
can never be decrypted, by anyone, since its salt and IV are not in the file.
The bot says so rather than failing vaguely.

That passkey is the one the source install used; it is unrelated to
`SDA_PASSKEY`, which is applied when accounts are written back out here.

The on-disk layout is identical to the desktop app — `manifest.json` plus one
`{steamid}.maFile` per account, same AES-256-CBC/PBKDF2 encryption. Accounts
move between the app and the bot by copying files. `tests/test_dart_parity.py`
pins that compatibility against vectors generated by the Dart code itself.

## Admin commands

| Command | What it does |
|---|---|
| `/accounts` | List accounts and open a per-account menu |
| `/code` | Steam Guard code for an account |
| `/confirmations` | Pending trades and market listings, accept/deny individually or in bulk |
| `/login` | Sign in by scanning a QR code — also refreshes an existing account |
| `/import` | Bulk import `.maFile` documents or a `.zip` of a maFiles folder |
| `/share` | Grant login-approval access via Telegram's contact picker |
| `/shares` | Who has access, with revoke buttons |
| `/whoami` | Your Telegram ID and role |
| `/cancel` | Abort the current step |

The per-account menu also exports the maFile and removes the account (removing
revokes every share for it).

### When a session expires

Steam sessions die eventually, and no refresh token can save them — Steam wants
the password again. `/accounts` marks which accounts need it, the account menu
shows session status, and any failure caused by it offers a **Re-login** button
right where it happened.

Re-login asks for **the password only**. The username comes from the maFile and
the Steam Guard code is generated from the stored shared secret, so there is
nothing else to type. Your password message is deleted the moment it is read,
and the resulting SteamID is checked against the account being refreshed — the
wrong credentials cannot overwrite the wrong account's session.

If a guest runs into an expired account, they are told plainly and **you get a
message with the Re-login button attached** — otherwise you would only find out
by reading the logs.

You can also send a QR image yourself — as admin you may approve a login for
any account, not just shared ones.

## Sharing an account

`/share` → pick the account → Telegram's native people picker opens → choose up
to 10 → done. Each person gets a message telling them what they can now do.

An account only appears in `/share` if it can actually approve logins: it needs
both a `shared_secret` and a live session.

## What a guest does

They send the bot a photo or screenshot of the Steam login QR code. The bot
decodes it, shows them the request's device, platform, location and IP, and
offers Approve or Deny. If more than one account is shared with them, they pick
which one first.

Telegram compresses photos, which occasionally blurs a code past recognition —
sending the screenshot as a *file* preserves it, and the bot says so when a
decode fails.

## Layout

```
telegram-bot/
├── steamguard/          # Port of the app's lib/core — no Telegram in here
│   ├── totp.py                 confirmation_hash.py    mobile_signature.py
│   ├── file_encryptor.py       qr_challenge.py         qr_image.py
│   ├── models.py               storage.py              web.py
│   ├── auth.py                 approval.py             confirmations.py
│   └── time_sync.py
├── bot/                 # Telegram layer
│   ├── access.py               # share registry — who may touch what
│   ├── middlewares.py          # rejects strangers before any handler runs
│   ├── filters.py              # IsAdmin / IsGuest
│   ├── pending.py              # in-memory, TTL-bounded QR requests
│   └── handlers/               # common, admin, sharing, guest
└── tests/
```

`steamguard/` knows nothing about Telegram and `bot/` knows nothing about
Steam's wire format, so either side can be worked on alone.

## Deploying

```bash
cd telegram-bot
cp .env.example .env          # fill in BOT_TOKEN, ADMIN_ID, SDA_PASSKEY
docker compose up -d --build

docker compose logs -f        # follow
docker compose ps             # includes health status
```

**Set `SDA_PASSKEY` before you deploy.** Without it the volume holds every
`shared_secret` in plaintext, and a server is a much likelier place to lose a
disk image than a laptop. Check what compose actually resolved:

```bash
docker compose config | grep SDA_PASSKEY
```

`DATA_DIR` from `.env` is ignored on purpose — compose pins it to `/data`
inside the container, because `environment` wins over `env_file`.

### The data volume

`sda-data` holds `manifest.json`, every `.maFile`, and `shares.json`. **Losing
it loses every authenticator you did not export.** It survives
`docker compose down`; `down -v` deletes it.

```bash
# Back it up
docker run --rm -v sda-bot_sda-data:/data -v "$PWD:/out" alpine \
  tar czf /out/sda-backup.tar.gz -C /data .

# Restore
docker run --rm -v sda-bot_sda-data:/data -v "$PWD:/in" alpine \
  tar xzf /in/sda-backup.tar.gz -C /data
```

Prefer a host directory? Swap the volume line for `- ./data:/data` and give it
to the container's user first, or it will start up unable to write:

```bash
mkdir -p data && sudo chown -R 10001:10001 data
```

### What the container is allowed to do

It holds every secret you have given it, so it gets as little as possible: a
non-root user (UID 10001), a read-only root filesystem with a 64 MB `noexec`
tmpfs for scratch, all capabilities dropped, `no-new-privileges`, and caps of
512 MB memory and 256 PIDs. It opens no ports — polling is outbound only.

### Health

`restart: unless-stopped` only catches a process that *died*. A polling loop
that wedges leaves the process alive and the bot useless, so a background task
touches `/data/.heartbeat` every 30s and the healthcheck fails once it is more
than 120s stale — Docker then restarts the container. `docker compose ps` shows
the state; `bot/heartbeat.py` is the mechanism.

### Upgrading

```bash
git pull && docker compose up -d --build
```

The volume is untouched, so accounts and shares carry over.

## Tests

```bash
pip install -r requirements-dev.txt
.venv/Scripts/python -m pytest
```

146 tests. The ones worth knowing about:

- **`test_dart_parity.py`** — runs the Python crypto against vectors emitted by
  the Flutter implementation and asserts byte equality for TOTP codes,
  confirmation hashes, mobile signatures, and AES ciphertext. Regenerate the
  fixture after any crypto change:

  ```bash
  dart run tool/export_crypto_vectors.dart > telegram-bot/tests/fixtures/dart_vectors.json
  ```

- **`test_access.py`** — that a share does not leak to another account or
  another user, that revocation works, and that one guest cannot act on
  another's pending QR request.
- **`test_qr_image.py`** — decoding clean screenshots, JPEG-compressed photos,
  inverted dark-theme captures, and oversized images.
- **`test_bulk_import.py`** — archives with nested folders, encrypted entries
  decrypted via their manifest, wrong-passkey reporting, and refusal of
  decompression bombs and oversized archives.
- **`test_qr_render.py`** — that what `/login` draws is readable by the same
  decoder that reads what users send, including a real above-int64 `client_id`.
- **`test_session_expiry.py`** — that an expired access token is treated as
  routine while an expired refresh token is not, and that a guest is never
  offered an account whose login is dead.
- **`test_heartbeat.py`** — that a stale heartbeat fails the healthcheck and a
  fresh one passes, so a wedged bot actually gets restarted.

## Not included

Linking a *new* authenticator (`AddAuthenticator` / `FinalizeAddAuthenticator`).
That flow needs email and SMS round-trips that are awkward in chat and much
easier in the desktop app — link there, then `/import` the maFile.
